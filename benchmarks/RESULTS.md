# Aegra и Valida: детерминированный граф с checkpoints

Замер выполнен 13 сентября 2026 года. **Исправление первоначального результата:** опубликованная ранее серия ошибочно ограничивала Valida четырьмя одновременными HTTP-запросами через стандартную очередь LangGraph SDK. Вывод о том, что Aegra быстрее при 50 параллельных запусках, был неверным. После явной установки `callerOptions.maxConcurrency=50` во всех шести новых сериях Valida выполнила этот граф быстрее: медиана **52,76 против 15,53 успешных запусков/с**. Эти цифры относятся только к описанной конфигурации и графу без LLM.

Причина ошибки в предыдущей методике: SDK по умолчанию допускает четыре одновременных запроса. Aegra отправляет заголовки `StreamingResponse` для `/runs/wait` до окончания графа, после чего SDK освобождает слот; Valida отправляет JSON-ответ после окончания графа и удерживала слот всё это время. Поэтому прежние серии сравнивали фактически разную параллельность запросов. [Исходник Aegra для `/runs/wait`](https://github.com/aegra/aegra/blob/bbc784646e6a3912cf05b6b9de0054fdf50a36b7/libs/aegra-api/src/aegra_api/api/runs.py#L361-L403), [обработчик Valida](../src/api/index.ts), [исправление клиента нагрузки](workload.ts).

Графы [Valida](../examples/benchmark/graph.ts) и [Aegra](aegra/graph.py) состоят из двух последовательных async-узлов `add` и `double`. Каждый ждёт 200 мс; вход `{ "seed": 7, "increment": 5 }` даёт `intermediate=12`, `result=24`. Вызовы идут через один и тот же `@langchain/langgraph-sdk` (`runs.wait`) на 50 отдельных threads, чтобы проверять сохранение checkpoints. После пяти прогревочных запусков измеряется 15 секунд idle, затем 10 волн по 50 запросов одновременно. Это burst-нагрузка с пределом 50, а не непрерывное удержание 50 исполняющихся графов. Все 3000 нагрузочных запусков завершились с верным результатом. В третьей серии каждой платформы PostgreSQL содержал по 40 LangGraph checkpoints на каждом из 50 threads после десяти запусков, то есть по четыре на запуск.

Исправленные серии шли в порядке Valida–Aegra–Aegra–Valida–Valida–Aegra. Между ними останавливалось приложение, перезапускались PostgreSQL и Redis, затем запускалось только следующее приложение. Aegra: [исходник `bbc7846`](https://github.com/aegra/aegra/commit/bbc784646e6a3912cf05b6b9de0054fdf50a36b7), версия 0.10.5, официальный Dockerfile и `uv.lock`, Redis broker с одним worker loop и лимитом 50 заданий. Valida: Bun 1.4.1, BullMQ, один API со встроенным worker и лимитом 50. Оба приложения ограничены 4 CPU и 4 GiB RAM без swap. Общие контейнеры: PostgreSQL 17.11 с pgvector (2 CPU, 1 GiB) и Redis 7.4.10 (1 CPU, 256 MiB), отдельные БД и Redis DB для каждой платформы. Машина: Linux x86-64, 16 логических CPU, 31 GiB RAM. На ней работали и другие контейнеры, поэтому это локальный сравнительный замер, а не результат на выделенном сервере. [Схема worker Aegra](https://docs.aegra.dev/guides/worker-architecture) описывает используемые параметры `WORKER_COUNT` и `N_JOBS_PER_WORKER`.

В прогретом idle Valida использует примерно на 56 MiB меньше RAM, а Aegra — примерно на 0,27% одного ядра меньше CPU. При нагрузке Valida быстрее и расходует меньше CPU на один успешный запуск, но достигает более высокого мгновенного пика CPU и примерно на 16 MiB большего пика RAM самого приложения. Пик памяти всего стека у Valida ниже примерно на 32 MiB; для сравнения используемой памяти надёжнее также смотреть на анонимную RAM, поскольку `memory.current` PostgreSQL включает файловый кэш.

`runs.wait` измеряет задержку SDK от запроса до ответа, включая очередь и ожидание API, а не только время исполнения двух узлов. На одиночном прогревочном запуске медиана составляла около 0,48 с для Valida и 2,02 с для Aegra. В использованном Redis worker mode [Aegra проверяет завершение с паузой 2 с](https://github.com/aegra/aegra/blob/bbc784646e6a3912cf05b6b9de0054fdf50a36b7/libs/aegra-api/src/aegra_api/services/worker_executor.py#L119-L138); это объясняет существенную часть задержки её `/runs/wait` в коротком сценарии. Эти цифры не означают, что само исполнение Python-графа занимает 2–3 секунды. Для разложения оставшейся задержки потребуется отдельное профилирование. При смене графа, числа потоков, режима worker или типа БД результаты могут измениться.
