# Aegra и Valida: детерминированный граф с checkpoints

Замер выполнен 13 сентября 2026 года. В этом сценарии Valida расходовала меньше RAM приложения, а Aegra быстрее обрабатывала 50 одновременных запусков: медианная скорость 18,89 против 7,99 запусков/с. Разница относится к этому конкретному графу и конфигурации, не к нагрузке с LLM.

Графы [Valida](../examples/benchmark/graph.ts) и [Aegra](aegra/graph.py) состоят из двух последовательных async-узлов `add` и `double`. Каждый ждёт 200 мс; вход `{ "seed": 7, "increment": 5 }` даёт `intermediate=12`, `result=24`. Вызовы идут через один и тот же `@langchain/langgraph-sdk` (`runs.wait`) на 50 отдельных threads, чтобы проверять сохранение checkpoints. После пяти прогревочных запусков измеряется 15 секунд idle, затем 10 волн по 50 запросов одновременно. Это **burst-нагрузка с пределом 50**, а не непрерывное удержание 50 исполняющихся графов. Все 3000 нагрузочных запусков завершились с верным результатом; в проверенной первой паре обе системы записали по четыре LangGraph checkpoint на запуск.

Серии шли в порядке Aegra–Valida–Valida–Aegra–Aegra–Valida. Между ними останавливалось приложение, перезапускались PostgreSQL и Redis, затем запускалось только следующее приложение. Aegra: [исходник `bbc7846`](https://github.com/aegra/aegra/commit/bbc784646e6a3912cf05b6b9de0054fdf50a36b7), версия 0.10.5, официальный Dockerfile и `uv.lock`, Redis broker с одним worker loop и лимитом 50 заданий. Valida: Bun 1.4.1, BullMQ, один API со встроенным worker и лимитом 50. Оба приложения ограничены 4 CPU и 4 GiB RAM без swap. Общие контейнеры: PostgreSQL 17.11 с pgvector (2 CPU, 1 GiB) и Redis 7.4.10 (1 CPU, 256 MiB), отдельные БД и Redis DB для каждой платформы. Машина: Linux x86-64, 16 логических CPU, 31 GiB RAM. На ней работали и другие контейнеры, поэтому это локальный сравнительный замер, а не результат на выделенном сервере. [Схема worker Aegra](https://docs.aegra.dev/guides/worker-architecture) описывает используемые параметры `WORKER_COUNT` и `N_JOBS_PER_WORKER`.

В таблицах — медиана трёх серий и диапазон в скобках. CPU `100%` означает полную загрузку одного ядра; пик считается по интервалам cgroup не короче 100 мс. RAM — `memory.current` cgroup, включая файловый кэш.

Valida экономит около 50 MiB RAM в прогретом idle и около 21 MiB на пике нагрузки. По idle CPU преимущество у Aegra, но абсолютная разница меньше 0,4% одного ядра. Пик CPU приложения у Valida в одной серии превысил Aegra, поэтому устойчивого преимущества по этому показателю не видно. По суммарному CPU на запуск и скорости в этом тесте лидирует Aegra. Разница в CPU PostgreSQL наблюдаема; установление причины потребует профилирования запросов. Valida записывала также журнал событий, и он может вносить вклад, но этот замер не доказывает причинность.

`runs.wait` измеряет задержку SDK от запроса до ответа, включая очередь и ожидание API. На одиночном прогревочном запуске Valida отвечала примерно за 0,48 с, Aegra — за 2,02 с; это не время выполнения только двух узлов. Файловый кэш PostgreSQL влияет на `memory.current` всего стека даже после рестартов, поэтому для оценки памяти приложения используйте первую таблицу и показатель анонимной RAM. При смене графа, числа потоков, режима worker или типа БД результаты могут измениться.
